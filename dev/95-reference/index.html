PowerPlotsMakie.PowerPlotsMakie — Module
PowerPlotsMakie

Plot power-system networks with Makie.

A Makie port of PowerPlots.jl, built on GraphMakie and NetworkLayout. The data model is pluggable: any package can teach PowerPlotsMakie about its networks by implementing the handful of functions in interface.jl. Support for PowerModels.jl network dictionaries ships as a package extension, loaded by using PowerModels.

source
PowerPlotsMakie.ACADEMIC_COMPONENTS — Constant

Per-component styling for academic_theme's monochrome mode.

Greyscale can only carry so much: four shades are already hard to tell apart in print, so the components are separated by shape and line style first and by shade second. The shapes follow one-line diagram convention as far as plain Makie markers allow — a generator is an open circle, a load a filled triangle pointing away from the bus, a shunt a diamond.

Covers the taxonomy the PowerModels backend supplies plus the other names in the interface; an unlisted component type still gets its colour from the usual palette rotation, so a custom backend is not left invisible, just not monochrome.

PowerPlotsMakie.ColorResult — Type
ColorResult

Resolved colours for one component type, plus what a legend or colorbar would need to describe them.

Everything is baked down to explicit RGBAf because the whole network is drawn by a single graphplot, and Makie has no notion of a per-index colormap: components with different colormaps can only coexist as literal colours. The legend metadata carried here is what lets the colorbars be rebuilt afterwards.

PowerPlotsMakie.Field — Type
Field(name)

Marks a plot attribute as driven by a data field rather than given literally.

color = :red is a constant colour; color = Field(:vm) colours each component by its voltage magnitude. The wrapper exists because a bare Symbol is ambiguous — :red is both a colour name and a plausible field name. PowerPlots.jl avoids the ambiguity by splitting the concept across two keyword arguments (:color and :data); marking the field is the same idea with one attribute instead of two.

components = Dict(:bus => (color = Field(:vm), colormap = :viridis))

PowerPlotsMakie.LayoutState — Type
LayoutState

Mutable positions plus the set of vertices the user has pinned.

This is the whole interaction model, and it is deliberately free of Makie: dragging, pinning and re-running the layout are ordinary functions over this struct, so they can be tested without a window. CI has no display, so anything that needed one would go untested. The Makie event handlers below are a thin shell that translates mouse and key events into these calls.

PowerPlotsMakie.NetworkGroups — Type
NetworkGroups

Which group every vertex and edge belongs to, and the colour each group is drawn in.

A group is a value of one node field — a bus's voltage level, its zone, its owner — and is what a plot of a large network is usually read by: "show me the 150 kV layer", "hide the foreign buses". Grouping does two things the per-component styling cannot: it colours nodes and the edges between them by the same key, and it lets whole groups be hidden without splitting the network into several plots.

vertex[i] and edge[j] are the group of vertex i and edge j, missing where there is none; edge_ends[j] holds the groups of edge j's two endpoints, which decide whether an edge between two groups — a transformer — is drawn when one of them is hidden.

PowerPlotsMakie.PowerEdge — Type
PowerEdge <: Graphs.AbstractEdge{Int}

An edge of a PowerGraph.

Unlike Graphs.SimpleEdge, several PowerEdges may connect the same pair of vertices: power networks routinely carry parallel circuits (of the MATPOWER cases, case5 has one extra circuit and case24 has four). mult distinguishes them, numbering the circuits between a given pair of buses from 1 upwards in insertion order. It is what the plotting code uses to fan parallel circuits apart, since GraphMakie's curve_distance_usage = automatic only bows antiparallel edges of a directed graph and would leave parallel circuits drawn exactly on top of each other.

source
PowerPlotsMakie.PowerGraph — Type
PowerGraph <: Graphs.AbstractGraph{Int}

An undirected graph that admits parallel edges, used as the topological backbone of a network plot.

Graphs.SimpleGraph silently collapses parallel edges, which would merge two circuits between the same buses into a single drawn line and cost them their independent colouring. PowerGraph keeps one edge per electrical component instead, so edges(g) yields exactly one entry per branch/transformer/switch/connector and GraphMakie's per-edge attribute vectors line up one-to-one with the network's edge components.

The adjacency list is deduplicated: parallel edges appear once in fadj. Multiplicity lives only in edges. That keeps adjacency_matrix, degree, dijkstra_shortest_paths and friends behaving as they would on the underlying simple graph — which is what the layout algorithms want — while ne(g) still counts every circuit, which is what the renderer wants. Do not "fix" this by pushing duplicates into fadj: it makes adjacency_matrix emit duplicate structural entries and double-counts degree.

source
PowerPlotsMakie.PowerGraph — Method
PowerGraph(nv, pairs)

Build a PowerGraph on nv vertices from an iterable of (src, dst) vertex pairs. The order of pairs is preserved by edges, so callers can keep a parallel vector of component references aligned with it. Repeated pairs become parallel edges with increasing multiplicity.

PowerPlotsMakie.PowerNetwork — Type
PowerNetwork

A power network prepared for plotting: the backend data, the PowerGraph built from it, and the component references that give every vertex and edge its meaning.

vertices[i] is the component drawn at vertex i, and edges[j] the component drawn as edges(graph)[j], so any per-index vector handed to GraphMakie can be traced back to the component it describes. Vertices are ordered node components first, then injections; edges are ordered edge components first, then the synthesized connectors.

Build one with powernetwork.

source
PowerPlotsMakie.RadialTree — Type
RadialTree(; roots, satellites, satellite_distance, component_gap)

A tree layout for radial networks, wrapping NetworkLayout's Buchheim.

Buchheim itself is strict: it demands a rooted tree given as a parent → child adjacency list with the root at vertex 1 and every node reachable, and it throws on anything else — including an ordinary undirected tree, whose symmetric adjacency makes every node look like the child of two parents. This wrapper does the work of meeting that contract: it splits the graph into connected components, roots each one, renumbers it, and maps the resulting coordinates back onto the original vertex numbering.

  • roots names preferred root vertices by index. The first one found in a component roots it; a component containing none is rooted at its highest-degree vertex. For a power network the roots are the reference buses, which is what radial_tree fills in.
  • satellites names vertices to place around their neighbour rather than as tree children — injections, which would otherwise be drawn as another level of feeder and make a two-level network look four levels deep. Each is fanned into the widest angular gap between its bus's tree neighbours, so it never sits on top of a branch.
  • satellite_distance is how far from the bus they sit, in Buchheim's units, where sibling nodes are two apart.
  • component_gap is the horizontal space left between islands.

Edges that are not part of the rooted tree — present only if this is forced onto a meshed network — are simply drawn as chords between the vertices the tree placed.

PowerPlotsMakie._PrecompileFixture — Type
_PrecompileFixture

A tiny network used only to exercise the plotting path during precompilation.

The first powerplot call in a fresh session spends around ten seconds compiling this package together with GraphMakie and Makie's recipe machinery, which is most of the delay before an interactive window becomes usable. Running the same path here moves that cost into package precompilation, where it is paid once at install time instead of on every startup.

It is a private backend rather than a PowerModels case because PowerModels is a weak dependency and is not available while this package precompiles. The fixture implements the same interface any backend does, so the code traced here is the code a real plot runs.

source
Makie.process_interaction — Method

Translate key events into re-layout and unpin.

KeysEvent fires on every change to the set of held keys, and a held key repeats. Acting on "is r in the set" would therefore re-run the layout many times over while the key is down — each run costs a few hundred milliseconds on a mid-sized network, so the window would appear to hang. Only the transition from released to pressed counts.

source
Makie.process_interaction — Method

Translate mouse events into drag! calls.

The vertex is identified on leftdown, not on leftdragstart. leftdragstart fires only once the pointer has already moved, by which time it is no longer over the node: with the default marker size, picking still finds the node 3 px from its centre but has moved on to a different plot by 6 px. Picking at drag-start therefore misses almost every drag.

pick forces a synchronous GPU readback, so it is confined to the leftdown branch rather than run on every mouse event.

Make hiding a powerplot hide everything it draws.

PowerPlotsMakie._group_section — Method
_group_section(plot, title, labels) -> Union{Nothing,NamedTuple}

The legend section for a grouped plot: one line-and-marker swatch per group, each linked to a toggle so that clicking it hides the group.

Makie's Legend hides and shows plots, while a group is a subset of one plot. So every group gets a stand-in: an empty, invisible-to-the-eye scatter whose visible is the group's visibility. The legend toggles the stand-in as it would any plot, and the stand-in writes the result into the plot's hidden_groups; a change to hidden_groups from code is written back the other way, so the legend's dimmed entries always match the plot. The stand-ins live in the figure's root scene, where an empty plot cannot disturb any axis' limits.

PowerPlotsMakie.autoscale_factor — Method
autoscale_factor(positions, viewport; min_pixels = MIN_NODE_PIXELS) -> Float64

How much to multiply every design-unit size by, for a layout of positions drawn into a viewport of viewport pixels.

Two things set it. Density: a node is drawn at NODE_SPACING_FRACTION of the distance to its nearest neighbour, so a five-bus case gets big buses and a five-hundred-bus case gets small ones, and neither is a wall of overlapping circles. Figure size: that distance is measured in data units and converted with the pixels-per-unit the axis will use, so doubling the figure doubles every size in it.

Zoom is deliberately not one of them. Markers stay put in pixels while the camera moves, which is what makes zooming into a dense corner of a network useful — the buses separate instead of growing with it. Neither is the layout: the recipe measures the positions but does not track them, so dragging a bus or re-running the layout rearranges the network without resizing anything in it.

The result is clamped: never below min_pixels (MIN_NODE_PIXELS unless the plot's autoscale_min says otherwise), never above MAX_NODE_VIEWPORT_FRACTION of the viewport's shorter side. It falls back to 1.0 — the unscaled look — whenever there is nothing to measure: a single vertex, a viewport of zero size, or a layout that has collapsed to a point.

PowerPlotsMakie.flow_arrows — Method
flow_arrows(net, positions, curve_distances, flow, sizerange;
            waypoints = nothing, hidden = nothing) -> FlowArrows

Place an arrow at the midpoint of every branch carrying a flow value.

The arrow points from the from-bus to the to-bus where the value is positive and the other way where it is negative, which is the sign convention PowerModels uses: pf is measured leaving the from-bus. Magnitude is taken as abs, scaled linearly across sizerange over the branches that have a value, so the arrows are comparable within one plot and never comparable between two.

The arrow sits on the drawn path, not on the straight line between the buses: parallel circuits are bowed apart, and an arrow at the chord midpoint would float off its own circuit and onto its neighbour. For the same reason a branch drawn along a route — given as per-edge waypoints, see route_waypoints — gets its arrow halfway along the route. Connectors never carry arrows — they are plumbing, and a generator does not have a direction along its stub. Nor do edges flagged in hidden, a mask over the edges: a branch in a hidden group has no line for its arrow to sit on.

Sizes are scaled over every branch with a value, hidden or not, so hiding a group does not resize the arrows left on screen.

PowerPlotsMakie.interactive! — Method
interactive!(ax, plot; algorithm = NetworkLayout.Stress, name = :powerplot) -> NetworkInteraction

Make a powerplot interactive:

PowerPlotsMakie.isradial — Method
isradial(net) -> Bool

Whether the buses and the branches between them form a forest.

PowerPlotsMakie.layout_positions — Method
layout_positions(net; layout = :auto, pin = nothing, projection = identity)
    -> Vector{Point2f}

Position every vertex of net. Coordinates from the data are first passed through projection, a function from point to point — web_mercator to draw longitude and latitude over web map tiles — and the layout works around them where they now lie.

layout accepts:

  • :auto — use the data's coordinates when every vertex has them; otherwise pick an algorithm for this network: RadialTree when the buses and branches form a forest (isradial), Stress otherwise. Data-supplied coordinates for some vertices, or an explicit pin, force Stress, since it is the choice that can honour them;
  • :radial — a RadialTree rooted at the reference buses, whether or not the network is a forest;
  • :stress — stress majorization, honouring pin;
  • a NetworkLayout algorithm, e.g. Stress() or Spring(; C = 3);
  • a vector of points, one per vertex, used as given;
  • any callable graph -> positions.

pin names vertices that must not move, as a collection of indices or a Dict of index => Bool. Vertices whose coordinates come from the data are pinned automatically, which is how PowerPlots.jl's fixed = true behaves — the difference being that here the pinning is expressed through NetworkLayout's own pin support rather than a bespoke layout, so it works with Spring, Stress and SFDP alike.

With :auto or :stress and every vertex with coordinates held, the vertices without — generators and loads, typically — are placed around the bus they hang off, a quarter of a typical line's length away whatever units the coordinates are in, and Stress lays out whatever is left.

PowerPlotsMakie.nearest_neighbor_spacing — Method
nearest_neighbor_spacing(positions; sample = SPACING_SAMPLE) -> Float64

The median distance from a vertex to its closest neighbour.

This is the length a node has to fit inside. A marker much bigger than it swallows its neighbours; one much smaller leaves a diagram of bare line segments. The median rather than the minimum, because one pair of nearly coincident buses should not shrink an entire plot.

At most sample vertices are measured — evenly spaced through the vertex list, so the answer is deterministic — each against every vertex. That bounds the cost at sample * N instead of N^2, which matters because this is recomputed while a node is being dragged.

Returns 0.0 for fewer than two vertices, and for a layout whose sampled vertices all sit on top of one another.

Saving a figure waits for the tiles in view to arrive. Tiles are requested with a User-Agent naming this package, user_agent, since the OpenStreetMap tile servers block requests that do not say where they come from; they also ask that tiles not be fetched in bulk. user_agent = nothing sends Tyler's default.

basemap returns the Tyler.Map behind a plot.

PowerPlotsMakie.powerplot — Method
powerplot(data; kwargs...)
powerplot!(ax, data; kwargs...)

Plot a power-system network.

data is anything a loaded backend understands — a PowerModels network dictionary, say — or a PowerNetwork built earlier with powernetwork.

The whole network is drawn as a single GraphMakie graphplot: buses and injections are vertices, branches and connectors are edges, and per-component styling is expressed as per-index vectors. Parallel circuits keep their own identity, and are fanned apart by parallel_spread.

Styling

Role-level attributes apply to every component of that role:

  • nodes: node_color, node_size, node_marker, node_strokewidth, node_strokecolor
  • edges: edge_color, edge_width, edge_linestyle
  • connectors: connector_color, connector_width, connector_linestyle

each with the usual Makie colour companions (*_colormap, *_colorrange, *_colormode, *_palette).

Per-component overrides go in components, keyed by component type:

powerplot(case;
    components = Dict(
        :bus    => (color = Field(:vm), colormap = :viridis),
        :branch => (color = Field(:rate_a), width = 3),
        :gen    => (color = :orange, marker = :rect),
    ),
)

A colour is constant unless it is wrapped in Field, which names a data field to colour by; numeric fields get a continuous ramp and everything else a categorical palette, overridable with colormode.

Sizing

Sizes are design units, not pixels. autoscale multiplies all of them — node sizes, edge and connector widths, flow arrows, stroke widths — by a single factor, so a plot keeps its proportions while its absolute size follows the figure it is drawn into and the density of the network it is drawing. A five-bus case gets big buses, a five-hundred-bus case small ones, and doubling the figure doubles everything in it.

Two things deliberately leave it alone. Zoom: nodes stay put in pixels as the camera moves, so zooming into a crowded corner separates them instead of magnifying them. And the layout: dragging a bus or re-running the layout rearranges the network without resizing anything in it, so the plot does not change weight under the interaction keys. The factor is remeasured when the network changes, when the figure is resized, and when autoscale is set.

autoscale = false turns it off and leaves every size in raw pixels; a number, such as autoscale = 1.4, scales the whole plot by hand. autoscale_min is the smallest node diameter, in pixels, the automatic factor will go down to: on a dense geographic network the measured spacing alone would leave markers too small to tell apart. See autoscale_factor for how the automatic factor is arrived at.

Flow arrows

flow = true draws an arrow along every branch that has a pf value — which a PowerModels case has once a solution has been merged into it — pointing the way the power goes and sized by how much of it there is. flow = Field(:qf) follows a different field. See flow_arrows for the geometry, and flow_color, flow_marker and flow_size for the styling.

Routes

A branch whose data carries a route — edge_coordinates, which for PowerModels is a coordinates list of [x, y] pairs on the branch — is drawn along it instead of as a straight line, from its from-bus through the route's points to its to-bus. routes = :auto does this only when every bus has coordinates of its own, since a route means nothing on a computed layout; true and false force it either way. Parallel circuits with routes are not fanned apart: two circuits sharing a corridor are drawn on top of each other, as they run. route_radius rounds the corners, in data units; 0 draws straight segments and nothing a smooth spline through the points.

Changing routes or route_radius on a plot that already exists takes effect at the next change of the node positions: GraphMakie redraws its edges when the positions or curves change, but not when only waypoints or waypoint_radius does.

Projection

projection is applied to every coordinate the data carries — bus coordinates and line routes — before anything is laid out or drawn: a function from point to point, by default identity. web_mercator turns longitude and latitude into the projection web map tiles use, which is what powermap draws the network over. route_radius and parallel_spread are in the projected units.

Line styles

A line style, like a colour, can come from the data: linestyle = Field(:name) in components (or as edge_linestyle), with linestyles (or edge_linestyles) saying which value is drawn how — Dict("cable" => :dash), a vector handed out over the values, or by default true dashed for a Bool field. Where the field holds one value per segment of the branch's route — a line that goes underground for part of its way — the route is drawn stretch by stretch, each in its own style:

powerplot(case;
    components = Dict(:branch => (linestyle = Field(:route_kind),
                                  linestyles = Dict("cable" => :dash))))

These stretches are drawn as straight segments whatever route_radius says. See resolve_linestyles and route_segments; powerlegend! adds a section that says what each style means.

Groups

group = Field(:base_kv) sorts the network into groups by a node field — voltage level, zone, owner — and colours every bus, branch and injection by its group, so one plot shows a multi-level network the way a map does. Branches and injections inherit the group of the buses they hang off; a transformer between two groups belongs to neither and keeps its component colour. group_palette sets the colours: a Dict from value to colour such as Dict(380 => :firebrick, 150 => :steelblue), a vector, or a colormap name. A component given a colour of its own in components or a role-level attribute is not recoloured.

hidden_groups lists groups not to draw; edges into a hidden group are hidden with it. powerlegend! gives each group an entry that toggles it on click. See network_groups for the rules.

Boundary nodes

Buses a backend reports through boundary_nodes — where the modelled network meets the equivalent of the grid around it — are drawn with boundary_marker, boundary_color and boundary_scale times their size, and get their own legend entry. boundary = false draws them like any other bus.

Hover

With Makie's DataInspector attached (DataInspector(fig)), hovering a bus or branch shows which component it is, followed by the fields named in hover_fields, e.g. hover_fields = [:name, :base_kv, :vm]. component_at answers the same question for hand-rolled readouts.

component_defaults takes the same shape and sits underneath components, which is where a theme puts its per-component styling — see academic_theme. Setting components overrides it component by component rather than wholesale.

Note that both must be a Dict (or a vector of pairs). A NamedTuple cannot be used here: Makie converts NamedTuple-valued attributes to Attributes and the nested per-component settings are lost in the process.

PowerPlotsMakie.resolve_color — Method
resolve_color(values, spec, scheme) -> ColorResult

Turn one component's colour specification into per-index colours.

values are the field values for that component's indices (only consulted when the spec names a Field), spec is the user's per-component settings, and scheme is the palette slot assigned by assign_schemes.

Four modes — PowerPlots' three, plus the usual Makie escape hatch:

  • a literal colour, or anything Makie can parse as one, gives a constant colour;

PowerPlotsMakie.resolve_linestyles — Method
resolve_linestyles(values, field, request) -> (; styles, segments, result)

Line styles for a component styled by a data field, linestyle = Field(field).

values holds the field for each edge. A scalar picks the edge's style. A vector holds one value per segment of the edge's route — a line that runs overhead, then underground, then overhead again — and is kept in segments for route_segments to draw; the edge's own style is then that of its most common value, which is what it is drawn in where it has no route to follow. missing is drawn solid.

request maps values to styles: a Dict such as Dict("cable" => :dash), matched as isequal with numbers compared by value, or a vector handed out over the sorted values. nothing draws false solid and true dashed for a Bool field, and otherwise hands out LINESTYLE_CYCLE. Values a Dict does not name are drawn solid.

PowerPlotsMakie.resync! — Method
resync!(interaction) -> interaction

Adopt the plot's current vertex positions as the interaction's own.

Writing to the plot's layout attribute — switching routing algorithm from a menu, say — recomputes the positions inside the recipe, which leaves the interaction still holding the positions from before: the next drag would snap the whole network back to the old layout. Call this after any such write to hand the new positions over.

Pins and the selection survive, minus any vertex the new layout does not have. Whether a pin still means anything afterwards is the caller's business: Stress, Spring and SFDP honour the plot's pin attribute, while the tree layouts have nowhere to put it and will move a pinned bus regardless.

route_segments(net, style, routes, mask, positions, colors, widths) -> Dict{Any,RouteLayer}

PowerPlotsMakie.route_waypoints — Method
route_waypoints(net, routes, positions) -> Vector{Vector{Point2f}}

The waypoints GraphMakie should draw each edge through, in edge order; empty for an edge with no route, which is then drawn as usual.

Each route is turned to run from the edge's from-node to its to-node, whichever way the data stored it, and the edge is drawn from the node, through every point of the route, to the other node. The route is not trimmed or stretched to meet the nodes: a line in the data seldom ends exactly on the coordinate a substation is drawn at, and the short hop between the two is more honest than moving either. It also means a bus dragged away from its coordinate stays connected, the end segments following it while the route stays put.
